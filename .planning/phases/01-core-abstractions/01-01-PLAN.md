<task type="auto">
  <name>Task 2: Implement message types with tool call round-trip support</name>
  <files>src/message.rs</files>
  <action>
Create `src/message.rs` with the following types. Follow the research-recommended design exactly.

**Role enum** (LOCKED per user decision):
```rust
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "lowercase")]
pub enum Role {
    System,
    User,
    Assistant,
    Tool,
}
```

Derive Serialize/Deserialize on Role because it maps directly to the OpenAI API's `role` field (this is a wire format concern, not a domain concern). Use `rename_all = "lowercase"` so `Role::System` serializes as `"system"`.

**Message struct** (LOCKED: Role + content String, with metadata per Claude's discretion):
```rust
#[derive(Debug, Clone, PartialEq)]
pub struct Message {
    pub role: Role,
    pub content: String,
    pub tool_calls: Option<Vec<ToolCall>>,
    pub tool_call_id: Option<String>,
    pub name: Option<String>,
}
```

Import ToolCall from crate::types: `use crate::types::ToolCall;`

The three optional fields support tool call round-trips (per research -- OpenAI requires tool_call_id on tool result messages, and assistant messages carry tool_calls when the model requests tools). Without these, Phase 3 tool calling would be impossible.

Do NOT add Serialize/Deserialize to Message -- it's an internal library type. The OpenAI provider (Phase 2) will have its own API-specific serde structs.

**Convenience constructors:**
- `Message::new(role, content)` -- sets all optional fields to None
- `Message::system(content)` -- shorthand for Role::System
- `Message::user(content)` -- shorthand for Role::User
- `Message::assistant(content)` -- shorthand for Role::Assistant
- `Message::tool_result(tool_call_id, name, content)` -- creates a Tool role message with metadata

All content parameters should accept `impl Into<String>` for ergonomic use with both &str and String.

Note: The user's locked decision specified `Message { role: Role, content: String }` as the base shape. The additional Optional fields (tool_calls, tool_call_id, name) are added per Claude's discretion area for "message metadata fields needed for tool call round-trips." The convenience constructors keep the common case (new/system/user/assistant) just as simple as the two-field version.
  </action>
  <verify>Run `cargo check`. The message module should compile. Verify Role has 4 variants, Message has 5 fields, and all 5 constructors exist.</verify>
  <done>src/message.rs contains Role enum with System/User/Assistant/Tool variants, Message struct with role + content + 3 optional metadata fields, and 5 convenience constructors. All types derive Debug + Clone + PartialEq.</done>

<task type="auto">
  <name>Task 3: Implement shared value types (ToolCall, ToolDefinition, ModelOptions, ModelResponse)</name>
  <files>src/types.rs</files>
  <action>
Create `src/types.rs` with all shared value types. These are pure data types with no behavior beyond construction.

**ToolCall** (LOCKED: name + arguments as raw JSON string; id added per research necessity):
```rust
#[derive(Debug, Clone, PartialEq)]
pub struct ToolCall {
    pub id: String,
    pub name: String,
    pub arguments: String,
}
```

The `id` field is essential for OpenAI tool call round-trips. The user's locked decision specified `{ name, arguments }` but research confirmed the API assigns each tool call a unique `id` (e.g., `"call_abc123"`) that MUST be echoed back in tool result messages. This is a necessary addition for correctness.

**ToolDefinition:**
```rust
#[derive(Debug, Clone, PartialEq)]
pub struct ToolDefinition {
    pub name: String,
    pub description: String,
    pub parameters: serde_json::Value,
}
```

The `parameters` field is a JSON Schema value describing the tool's parameters. Using `serde_json::Value` keeps it flexible -- the framework doesn't need to parse or validate the schema itself.

**ModelResponse** (Claude's discretion -- enum chosen because OpenAI returns content XOR tool_calls, never both):
```rust
#[derive(Debug, Clone)]
pub enum ModelResponse {
    Text(String),
    ToolCalls(Vec<ToolCall>),
}
```

Add convenience accessor methods:
- `pub fn text(&self) -> Option<&str>` -- returns Some(&str) for Text variant
- `pub fn tool_calls(&self) -> Option<&[ToolCall]>` -- returns Some(&[ToolCall]) for ToolCalls variant

**ModelOptions** (Claude's discretion -- minimal with builder-lite pattern):
```rust
#[derive(Debug, Clone)]
pub struct ModelOptions {
    pub temperature: Option<f64>,
    pub max_tokens: Option<u32>,
}
```

Implement `Default` (both fields None) and `ModelOptions::new()` (returns default). Add builder methods:
- `pub fn with_temperature(mut self, temperature: f64) -> Self`
- `pub fn with_max_tokens(mut self, max_tokens: u32) -> Self`

All types use owned types (String, Vec) -- no lifetime parameters. This follows the research recommendation for owned types at async boundaries.
