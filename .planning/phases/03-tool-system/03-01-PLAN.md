**Tool trait:**

```rust
use async_trait::async_trait;
use crate::error::Result;
use crate::types::ToolDefinition;

#[async_trait]
pub trait Tool: Send + Sync {
    /// The unique name of this tool (e.g., "calculator", "get_weather").
    fn name(&self) -> &str;

    /// A human-readable description of what this tool does.
    /// Sent to the model to help it decide when to use this tool.
    fn description(&self) -> &str;

    /// JSON Schema describing the tool's parameters.
    /// The developer builds this explicitly using serde_json::json!().
    fn parameters(&self) -> serde_json::Value;

    /// Execute the tool with the given arguments.
    ///
    /// `args` is the parsed JSON arguments from the model's tool call.
    /// Returns a string result that will be sent back to the model as
    /// the tool's output.
    async fn execute(&self, args: serde_json::Value) -> Result<String>;

    /// Build a ToolDefinition from this tool's metadata.
    ///
    /// Default implementation assembles a ToolDefinition from name(),
    /// description(), and parameters(). Override only if you need custom behavior.
    fn definition(&self) -> ToolDefinition {
        ToolDefinition {
            name: self.name().to_string(),
            description: self.description().to_string(),
            parameters: self.parameters(),
        }
    }
}
```

Key design choices per CONTEXT.md/RESEARCH.md:
- `async fn execute` via `#[async_trait]` -- matches Model trait pattern
- `Send + Sync` supertraits -- matches Model, required for async task sharing
- `serde_json::Value` input -- parsed once at dispatch, not in every tool
- `String` output -- matches OpenAI's tool result content field exactly
- `Result<String>` -- uses framework's Error type per locked decision
- Default `definition()` method -- assembles ToolDefinition from the individual methods
- Separate methods (name, description, parameters) rather than metadata struct -- reads naturally as educational code

**ToolRegistry struct:**

```rust
use std::collections::HashMap;
use crate::error::Error;

pub struct ToolRegistry {
    tools: HashMap<String, Box<dyn Tool>>,
}
```

Implement these methods:

- `ToolRegistry::new() -> Self` -- creates empty registry
- `ToolRegistry::register(&mut self, tool: Box<dyn Tool>) -> Result<()>` -- inserts tool by name, returns `Err(Error::DuplicateTool(name))` if name already registered. Uses `tool.name().to_string()` as the key.
- `ToolRegistry::get(&self, name: &str) -> Option<&dyn Tool>` -- looks up a tool by name, returns reference to the trait object
- `ToolRegistry::definitions(&self) -> Vec<ToolDefinition>` -- calls `definition()` on every registered tool and collects into a Vec. This is the bridge to `Model::chat_with_tools()`.

Add comprehensive doc comments on the struct and each method, explaining the educational purpose. For example, the struct doc comment should explain that ToolRegistry owns tools via `Box<dyn Tool>` which gives a simple lifetime story -- tools live as long as the registry.
