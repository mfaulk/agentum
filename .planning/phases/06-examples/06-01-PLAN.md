Create `examples/tool_calling.rs` demonstrating the Tool trait, ToolRegistry, and the full tool-calling round trip.

**Structure:**
1. Top-of-file doc comment block (`//!`) explaining: defining tools via the Tool trait, registering them, sending tool definitions to the model, handling both `ModelResponse::Text` and `ModelResponse::ToolCalls`, and dispatching tool calls back through the registry. Mention `OPENAI_API_KEY` requirement.

2. Imports -- crate root re-exports plus what's needed for Tool impl:
   - `agentic_framework::{Message, Model, ModelOptions, ModelResponse, OpenAiProvider, Tool, ToolRegistry}`
   - `agentic_framework::error::Result` (for Tool::execute return type)
   - `async_trait::async_trait`
   - `serde_json::json`

3. **Define two tool structs inline** (per user decision: self-contained, no shared modules):

   **Calculator tool:**
   - `struct Calculator;`
   - `#[async_trait] impl Tool for Calculator` with:
     - `name() -> "calculator"`
     - `description() -> "Performs basic arithmetic operations (add, subtract, multiply, divide)"`
     - `parameters()` -- hand-written JSON Schema using `json!({...})`:
       ```
       {
         "type": "object",
         "properties": {
           "operation": { "type": "string", "enum": ["add", "subtract", "multiply", "divide"] },
           "a": { "type": "number" },
           "b": { "type": "number" }
         },
         "required": ["operation", "a", "b"]
       }
       ```
     - `execute()` -- parse operation, a, b from args. Perform real computation. Return result as string (e.g., `"Result: 15.0"`). Handle unknown operation with an error message string (not an Err -- just return "Unknown operation: ...").
   - Add inline comment: "JSON Schema is hand-written -- the framework passes it to the model as-is."

   **GetWeather tool:**
   - `struct GetWeather;`
   - `#[async_trait] impl Tool for GetWeather` with:
     - `name() -> "get_weather"`
     - `description() -> "Gets the current weather for a given city"`
     - `parameters()` -- hand-written JSON Schema:
       ```
       {
         "type": "object",
         "properties": {
           "city": { "type": "string", "description": "The city name" }
         },
         "required": ["city"]
       }
       ```
     - `execute()` -- return realistic fake data (e.g., `"Weather in {city}: 72F, partly cloudy"`). Add inline comment: "In a real application, this would call a weather API."

4. **Main function** (`#[tokio::main] async fn main()`):
   a. **API key check:** Same pattern as simple_chat.rs -- manual env var check, helpful error, `exit(1)`.
   b. **Create provider:** `OpenAiProvider::new(api_key, "gpt-4o-mini")`
   c. **Register tools:**
      ```rust
      let mut registry = ToolRegistry::new();
      registry.register(Box::new(Calculator)).expect("register calculator");
      registry.register(Box::new(GetWeather)).expect("register weather");
      ```
      Add inline comment: "register() returns Err on duplicate names -- .expect() is safe here because we control the names."
   d. **Build messages:** System message explaining available tools, user message that will likely trigger a tool call (e.g., "What is 15 multiplied by 7?").
   e. **Get tool definitions:** `let tool_defs = registry.definitions();`
   f. **Call model with tools:** `provider.chat_with_tools(&messages, &tool_defs, &options).await` -- handle error like Task 1.
   g. **Handle BOTH response paths** (per user decision -- this is critical):
      ```rust
      match response {
          ModelResponse::Text(text) => {
              // The model chose to respond directly without calling a tool.
              println!("Direct response: {text}");
          }
          ModelResponse::ToolCalls(tool_calls) => {
              // The model wants to call one or more tools.
              // Display what the model requested, then dispatch.
              for tc in &tool_calls {
                  println!("Tool: {}", tc.name);
                  println!("Arguments: {}", tc.arguments);
              }
              // Dispatch all tool calls through the registry.
              let results = registry.dispatch_all(&tool_calls).await;
              match results {
                  Ok(messages) => { /* print each result */ }
                  Err(e) => { /* print error */ }
              }
          }
      }
      ```
   h. **Formatted output:** Section headers (`--- Tool Calling Example ---`), blank line separators, labeled values.

**Inline comments at key points:**
- Why `chat_with_tools` vs `chat` (model needs tool definitions to decide)
- Why match both variants (model may answer directly OR request tools)
- Why `.expect()` on register is safe (controlled input)
- Why dispatch returns Messages (tool results go back to model in multi-turn)

Do NOT use `.unwrap()` on fallible operations without explanation. The `.expect()` on `register()` is acceptable because the tool names are hardcoded constants.

Create `examples/workflow.rs` demonstrating the WorkflowBuilder API with a concrete, realistic use case: **summarize-then-translate** (per research recommendation).

**Use case:** A two-step LLM pipeline where step 1 summarizes an article into a concise English summary, and step 2 translates that summary into Spanish. A transform step at the beginning injects the article text, demonstrating all three concepts: transform steps, LLM steps, and data flow.

**Structure:**
1. Top-of-file doc comment block (`//!`) explaining: building workflows with the builder API, defining LLM steps and transform steps, connecting them with edges, and how data flows from one step to the next. Mention `OPENAI_API_KEY` requirement.

2. Imports:
   - `agentic_framework::{ModelOptions, OpenAiProvider, Workflow}`
   - `serde_json::json`

3. **Define article text** as `const ARTICLE: &str = "..."` at module level. Use a short (3-4 sentence) paragraph about a technology topic -- something the model can meaningfully summarize. Keep it brief so the example runs fast and cheap.

4. **Main function** (`#[tokio::main] async fn main()`):
   a. **API key check:** Same pattern as other examples.
   b. **Create TWO provider instances** -- one for each LLM step. Add inline comment: "Each LLM step owns its model (Box<dyn Model>), so we create separate providers. The underlying reqwest::Client handles connection pooling." Clone the api_key string before passing to the second provider.
   c. **Build workflow using the builder API:**
      ```rust
      let workflow = Workflow::builder()
          // Step 1: Inject the article text as structured data.
          .transform_step("inject_article", |_inputs| {
              Ok(json!({ "article": ARTICLE }))
          })
          // Step 2: Summarize the article in English.
          .llm_step(
              "summarize",
              Box::new(summarize_provider),
              |inputs| {
                  let article = inputs["inject_article"]["article"]
                      .as_str()
                      .unwrap_or("No article provided");
                  format!(
                      "Summarize the following article in 2-3 sentences:\n\n{}",
                      article
                  )
              },
          )
          // Step 3: Translate the summary to Spanish.
          .llm_step(
              "translate",
              Box::new(translate_provider),
              |inputs| {
                  let summary = inputs["summarize"]
                      .as_str()
                      .unwrap_or("No summary provided");
                  format!(
                      "Translate the following English text to Spanish:\n\n{}",
                      summary
                  )
              },
          )
          // Wire the data flow: inject -> summarize -> translate
          .chain(&["inject_article", "summarize", "translate"])
          .build();
      ```
      Handle the `build()` Result -- on error, print the builder errors and exit.
   d. **Execute workflow:** `workflow.execute().await` -- handle error.
   e. **Read results:** Access specific step outputs from the returned HashMap:
      ```rust
      if let Some(summary) = outputs.get("summarize") {
          println!("English Summary:\n{}", summary.as_str().unwrap_or("..."));
      }
      if let Some(translation) = outputs.get("translate") {
          println!("Spanish Translation:\n{}", translation.as_str().unwrap_or("..."));
      }
      ```
   f. **Formatted output:** Section headers for each stage (`--- Workflow Example: Summarize & Translate ---`, `--- Article ---`, `--- English Summary ---`, `--- Spanish Translation ---`).

**Inline comments at key points:**
- Why transform_step for injecting data (no LLM call needed, just data setup)
- Why .llm_step takes Box<dyn Model> (trait object for dynamic dispatch)
- How prompt_builder closures access upstream outputs via `inputs["step_name"]`
- Why .chain() (convenience for linear pipelines)
- Why .build() validates the graph (catches cycles, missing steps, etc.)
- How execute() returns all step outputs in a HashMap

**Important implementation details:**
- Use `ModelOptions::new().with_max_tokens(512)` for the LLM steps via the llm_step method. Note: the simple `llm_step()` method uses `ModelOptions::default()` internally. This is fine -- add a comment noting that custom options would require `llm_step_with_tools()` or the lower-level `step()` method. Actually, looking at the builder API, `llm_step()` always uses `ModelOptions::default()`. That's acceptable for this example. Add a comment: "llm_step() uses default model options. For custom temperature or max_tokens, use llm_step_with_tools() or the lower-level step() method."
- Use `gpt-4o-mini` for both LLM steps.
- The `.unwrap_or()` calls in prompt_builder closures are acceptable since the closures are fallible-tolerant (they provide defaults). Add a brief comment explaining this.
